# 目標（COPM）の読み取りに AI を使う案（検討メモ）

2026-11-10 時点の検討メモです。**今回のリリースには載せません。** 追加の費用と開発がかかるため、別の提案として PdM に出し、複数の API で実験して結果を比べてから導入するかを決めます。今回のリリースは語彙表による判定（仕様の M5・付録F）のままです。ただし、候補から足した目標の行には選んだ候補（`copm[].wantId`）を持たせ、入力画面で薄く見せて、候補の文も語彙表で読むようにしました（下の「これまでの経緯」）。

## いまの仕組みと困っていること

- 目標ごとの「優先する領域」（目標ブロック）は、目標文とメモに語彙表（`GOAL_VOCABULARY`）の語が含まれるかで点を足して決めています（`report/logic.ts` の `goalBlocksOf`）。
- 自由に書いた目標は語彙表に当たらない言い回しになりやすく、そうなると優先する領域が空欄になります。空欄になっても、入力画面では誰も気づけません。
  - 例：「縄とび」「前とび」は当たりません。語彙表にあるのは「縄跳び」「なわとび」です。
- 語句からブロックへ直接つなぐ方法が粗いことも問題です。候補24件のうち運動の9件（縄跳び・鉄棒・跳び箱・マット・自転車・水泳・かけっこ・スキップ・遊具）は、すべて「前庭覚・バランス・姿勢」になります。仕様のロジックのタブにも同じ指摘があります。

## これまでの経緯

- もとは「できるようになりたいこと」の候補を選んだ状態（`wants`）を保存し、それを判定に使っていました。しかし、目標の文言を大きく書き換えても選択が残るなど、候補と目標の行の状態が食い違いました。そのため 2026-10-21 に保存をやめました（マイグレーション `0006_remove_wants`）。
- 前回から引き継いだ目標は文言を変えられません（§2.3）。そのため、食い違いが起きるのは同じ回の中で書き換えたときだけです。
- 候補を目標の行に「種類」のチップとして付ける案も考えました。ただ、裏で候補の文を語彙表に通すだけなら、結局は語句マッチのままです。そこで、次の「ベース目標」の案にしました。
- 今回のリリースでは、PdM の意向で、その手前までを入れました（2026-11-10）。候補から足した行に候補の id（`wantId`）を持たせ、「目標 N」の横に薄く出し、コーチが「外す」で外せるようにしています。判定は、目標文・メモに候補の文を足して語彙表で読むだけです。AI を入れるときは、この `wantId` をコーチが確定したベース目標として読み替えられます。

## 提案

```
目標の文言・メモ ──(AI がベース目標を確率つきで選ぶ)──▶ ベース目標 ──(PdM が決める対応表)──▶ ブロック
                     コーチが画面で確かめ、直せる               画面に出すのはここまで       判定はコードで計算
```

1. **ベース目標の層を置きます。** 候補（いまの24件を出発点にする）ごとに、PdM・シニアコーチがブロックとの対応表を1行ずつ決めます。語彙表から機械的に作ることはしません。
2. **AI は「文言 → ベース目標」の分類だけを受け持ちます。** ベース目標と「該当なし」から選ばせ、選択肢ごとの確率を返させます。
3. **ブロックはコードで計算します。** 確率の高いベース目標（例：上位2件で確率 0.2 以上）の対応表を、確率で重み付けして足します。合計の高い3つが優先する領域です。
   - 例：「友だちとドッジボールで遊べる」→ 球技 0.7・友だちと遊ぶ 0.3 → 球技の表×0.7 ＋ 友だちの表×0.3 の上位3ブロック。
4. **AI を呼ぶのは入力のときだけです。** 結果は回のデータに保存し、レポート生成は保存した値を読むだけにします。レポートは決定的なまま（§7.2）で、作り直しても AI を呼びません。

### AI にブロックを直接出させない理由

ブロックまで直接出させる案（対応表をプロンプトで渡し、根拠として似ているベース目標も出させる）も検討しました。ベース目標に当てはまらない目標にも柔軟に答えられる利点はありますが、採りませんでした。理由は次の3つです。

- **根拠と結果がずれます。** 「縄跳びに似ている」と出しながら、縄跳びの表に無いブロックを返すことがあります。上の案なら、表示するベース目標がそのまま計算に使われるので、根拠と結果が必ず一致します。
- **対応表がただの参考情報になります。** AI が表と違う答えを出せるので、表を直しても判定が思ったとおりに変わる保証がありません。表を変えるたびに、プロンプトの調整と評価のやり直しが必要になります。
- **評価が難しくなります。** ベース目標の分類は正解率で測れます。ブロック3つの組み合わせ（455通り）は、専門家が1件ずつ採点しないと評価できません。

どれにも当てはまらない目標は「該当なし」として残します。その一覧からベース目標を増やしていきます。

### 画面のイメージ

```
目標 1                                      ベース：🪢 縄跳び ▾
┌──────────────────────────────────┐
│ 前跳びを10回続けて跳べる             │
└──────────────────────────────────┘

（同じ行を大きく書き換えた場合）
目標 1                                      ベース：🪢 縄跳び ▾
┌──────────────────────────────────┐
│ 妹と仲良く遊べる                     │
└──────────────────────────────────┘
  文言からは「👫 友だちと遊ぶ」に近いようです   [変える] [このまま]

（自由に書いた行。AI の推定は破線のチップで出し、押すと確定・変更）
目標 2                               ベース：⚾ 球技 ＋ 👫 友だちと遊ぶ（推定）▾
```

- 入力画面に出すのはベース目標の名前だけです。ブロックや語句は出さず、コーチ用の紙面の「目標ごとの優先する領域」にだけ出します。
- 候補から足した行と、事前アンケートで選ばれた項目から入れた行は、ベース目標を最初から確定にします。AI を呼ぶのは、自由に書いた行と書き換えた行だけです。
- 書き換えた後の文言を AI が読み直し、選んであるベース目標と合わなければ知らせます（語句マッチでは誤検知が多くてできなかったこと）。
- AI が使えないときは、コーチが候補のダイアログから選びます。入力やレポート作成は止めません。

### データの持ち方（案）

- `copm[].base = { goals: [{ id, probability }], by: 'coach' | 'ai' }` のような形にします。JSON の中の optional な項目なので、DB のマイグレーションは要りません。今回入れた `wantId` は `{ goals: [{ id: wantId, probability: 1 }], by: 'coach' }` として読み替えます。
- ベース目標は目標と一緒に次の回へ引き継ぎます。文言は変えられませんが、ベース目標は付け直せるようにします。
- ベース目標の変更は「未反映の変更」に含めます。
- 公式リリース前に入れるなら、語彙表は廃止できます。

## API の比較

### コスト（1000レポートあたり）

前提：

- 1レポートあたり目標6件なので、1000レポートで 6,000 判定です。為替は 1ドル＝160円で計算しています。
- 案A（ベース目標の確率を返す）：入力 約2,000トークン、出力 約100トークン。
- 案B（対応表とブロックの定義も渡してブロックまで出す）：入力 約4,000トークン、出力 約200トークン。
- トークン数は日本語の目標文とベース目標25件（説明つき）を想定した、ざっくりの見積もりです。

| API | 単価（100万トークンあたり） | 案A | 案B |
| --- | --- | --- | --- |
| Claude Haiku 5.5 | 入力 $0.10／出力 $0.50 | 約240円 | 約480円 |
| GPT-6 Luna | 入力 $0.10／出力 $0.50 | 約240円 | 約480円 |
| OpenAI Decisions API（GPT-6 Luna） | 入力 $0.10／出力は課金なし | 約190円 | 約380円 |
| Jev（TypeSafe） | 入力 $0.042／出力は課金なし | 約80円 | 約160円 |

- どれも1レポートあたり1円未満です。書き直しのたびに判定し直して呼び出しが2倍になっても、1000レポートあたり1,000円以下に収まります。**コストでは差がつきません。**
- Haiku 5.5 は思考が既定でオンで、思考のトークンは出力として課金されます。分類では思考を切るか、effort を low にします。
- 1世代前の GPT-5.6 Luna は単価が倍程度（入力 $0.20／出力 $1.20）で、案Aで約500円です。

### コスト以外

| | 日本語 | 提供状況（2026-11 時点） | 出力の形 |
| --- | --- | --- | --- |
| Haiku 5.5／GPT-6 Luna | 汎用の LLM なので問題なさそう | 一般提供 | JSON で返させる。割合は自己申告で、裏づけのある確率ではない |
| Decisions API | 明記なし（中身は GPT-6 Luna） | 一般提供（公式ガイド） | `choice` の質問で、選択肢ごとの確率と確信度を返す。案Aにそのまま合う |
| Jev | 英語が主。日本語などは英語と同等ではない、と案内されているとのこと（二次情報） | 新規登録の一時停止など、使えるアカウントにばらつきがある（二次情報） | 確率つきで選ぶ。案Aに合う |

- いまの第一候補は **案A を Decisions API で作る** ことです。ベース目標を `value` と `description` で渡せば、確率がそのまま返ってきます。
- Jev は最安ですが、差額は1000レポートあたり100円ほどで、日本語の精度と使えるかどうかのリスクに見合いません。
- 単価・提供状況は変わりやすいので、提案の時点で改めて確かめます。

## 導入前の実験

1. **評価セットを作ります。** 候補24件の文、その言い換え（「縄とび」「前とび10回」など）、staging の実際の目標に、正解のベース目標を付けます。正解は PdM・シニアコーチに付けてもらいます。
2. **複数の API で正解率を比べます。** Decisions API を本命に、Haiku 5.5（構造化出力）・GPT-6 Luna・Jev で同じセットを判定させ、正解率と「該当なし」の扱いを比べます。
3. **アプリのテストでは分類器を差し替え、API を呼びません。** 評価は別のスクリプトで行います。

## 決めること（PdM）

- ベース目標の一覧と、ブロックへの対応表。24件の候補をそのまま使うか、粒度をそろえて組み直すかを決めます。「該当なし」のとき、優先する領域を空にするか仮のブロックを当てるかも決めます。AI を入れるかどうかに関係なく必要で、いちばん時間がかかる作業です。
- 「初期リリースでは LLM を呼ばない」（AGENTS.md §13）の変更。
- 目標の文言とメモを外部の API に送ってよいか。名前や ID は送りません。それでも、社内のルールや保護者への説明として問題ないかの確認が要ります。Decisions API のゼロデータ保持（ZDR）は対象の顧客に限られます。ログに目標の文言を出さないルール（§13）は守ります。
- 追加の費用（上の表）と、開発の工数。
